# Muse 与 Codex 两桥并用、切换规划（讨论候选）

版本：2026-11-17。依据固定源码 `705232adbb8d6efad24b3a11979d93ae3bad6e7d` 与已有文字实测记录。本轮只出方案，待用户确认；没有修改、迁移或重启任何实例，也没有新增账号、凭据、监听或真实请求。

## 给用户看的简明版

我们暂时把产品叫作：**第一桥 Muse，第二桥 Codex**。第二桥当前接到的是 **PEPE／dot2api**，本机 Codex 命令行是另一种接法。开发对话仍是 01 公共底座、02 Muse、03 Codex，不跟着产品序号重排。

**建议先让两个桥各自正常使用，再做“一个微信入口，选择由谁回答”。** 当前已有的切换代码只能当作基础，不能直接把两个正在不同电脑上运行的桥拼起来。

本轮独立 QA 还复现了一处切换缺口：PEPE 已经答完，但微信发送结果不明确时，记录进入待核对的失败目录；现有切换命令仍可能显示“已切换”，状态查询也没有完整呈现这项发送不明。**这是单入口切换上线前由 01 必须修复的一项 P2 问题。** 要做到“回复去向未核清时先拒绝切换、状态里看得到、核对后才解锁”，不能把现有切换基础当成已经满足这项要求。当前独立 PEPE 入口未启用其他目标，此复现不等于发生过线上自动改派或重复执行。

| 阶段 | 用户能做什么 | 需要补什么 | 验收后才进入下一步 |
|---|---|---|---|
| 现在：两个桥各用各的 | 分别找 Muse 或 Codex／PEPE 聊天；一边故障不改另一边的账号和状态 | 给入口标清名字、能力和已测范围；记录各自运行版本 | 两边在同一测试窗口分别收发、交错发消息，无串线、无竞争收件。当前不是联合验收通过 |
| 下一步：同一入口切换，先只做文字 | 查看当前助理；空闲时切到 Muse 或 Codex；收到明确切换回执 | 一个统一收件处；两边可到达的执行通道；受控迁移及回退。当前跨主机 Muse 通道尚未建立 | 切换前后消息归属正确；忙时拒绝切换；断线、重启和迟到回复不会投错人或重做任务 |
| 再下一步：指定交给谁、显式交接 | “这段请交给 Codex”；得到标明来源的回复 | 独立任务记录、可预览的交接摘要、能力检查 | 只转用户选择的文字或附件；两个助理不自动复制全部记忆，不重复执行同一个任务 |
| 后续：附件、进度与恢复 | 统一找附件、看任务进度，遇到待核对状态知道如何处理 | 按助理区分能力的附件接入；可审计的未知任务核对与恢复入口 | Muse 原有附件能力不退步；PEPE 图片/文件另行通过真实验收，不能因文字跑通就标可用 |

现在两个入口使用的是隔离的微信绑定。**同一微信账号是否允许同时绑定并使用两个独立机器人，还没有由本项目实测确认。** 双入口方案不承诺无需切换微信账号；如果目标就是只用一个账号、一个聊天框，最终应走“统一收件处”方案。

### 一个入口放在哪里

短期最少新增接线的候选，是让**能运行 Muse Hook 的现有 Muse 云机承担统一收件**，继续用本地 Muse 执行链，再经受限 HTTPS 通道把 Codex 任务交给已有 PEPE 队列。这样不需要先造一个远程 Muse 执行器。但必须先验证 Muse 云机到该服务的网络、认证引用和生命周期，完成附件与状态迁移设计；目前尚未证明可以直接部署。

另一种是把统一收件放在独立常驻 VPS：PEPE 现有路线较接近，但 Muse 现在靠自己的平台 Hook 和本地文件收件，VPS 不能直接唤醒它。须另做一个正式的远程 Muse 取单和回执通道，因此改动更大。**不能仅修改一个模型名字，也不能让两台机器同时轮询同一个微信机器人。**

在选定并验证统一宿主之前，两条现有桥保持独立。首个单入口候选应先在隔离测试身份/状态上验证；正式接管原入口要有保留队列、游标和回执的迁移与回退计划，不能清空状态来换配置。

### 切换时的体验

- 一眼看到“当前：Muse”或“当前：Codex（PEPE）”。现有 `/backend` 可以查看名称；中文命令或菜单属于拟增加体验。
- 只在当前任务、排队任务和待发回复均处理清楚时切换。切换只影响之后的新消息，已有任务固定给原助理，不能中途改派。
- “切到 Codex”在产品里应明确映射到 PEPE。现有代码里的 `codex` 指本机 Codex 驱动，`pepe` 才是当前云端这条；不能把两者混用。
- 超时或回复去向不明时，显示“待核对”，保留原任务。不能偷偷换另一个助理再做一次。
- 切换助理不等于同步记忆。先保留两边各自的上下文；需要衔接时，由用户明确选择一小段任务摘要转交。电脑 PEPE 主聊和微信任务的记忆互通仍未验证。
- Muse 和 PEPE 的权限确认方式不一样。PEPE 继续沿用自身平台权限与确认；本轮文字接入不承诺微信逐工具审批。

### 分工与先后

1. 00 完成本次 QA 和独立分支上传，记录固定版本与已测边界。
2. 01 设计统一路由、任务归属、忙闲切换、状态迁移、附件能力与未知状态恢复的公共契约；02 核实 Muse Hook 与候选统一宿主的实际限制；03 核实 PEPE 专用队列的认证、断线补扫和回执。这一阶段先交方案，用户确认后才实施。
3. 先验双桥并用，再验隔离的单入口文字切换；保留 Muse 现有入口作为可恢复基线。文字通过后，再逐项扩展附件和显式任务交接。

难度判断：双独立桥并用主要是运行核对和联合验收；单入口文字切换涉及状态迁移和平台接线，属于中等以上工作；跨助理记忆/附件和可靠远程取消则是更大的独立批次。本方案不编造天数、成功率或“24 小时稳定”承诺。

## 技术附录：已存在的基础与实际缺口

以下路径/行号均相对固定 `705232a` 源树，并不代表线上新配置已经采用。

### A. 当前路由不是跨主机 Muse 执行器

- `dispatcher.py:119–130` 已实现 `/backend`，仅允许已配置名称，并在 `_busy` 为真时拒绝。`95–102` 把未结束任务、待发布/unknown 输出、legacy 收件和 pending/sending 回复视为忙；`199–217` 在入队时冻结 backend、instance、route_revision 和 conversation_key。
- `dispatcher.py:200–205` 的 Muse 分支只是把原记录交回**同一个 Store 的本地 legacy inbox**。`backends/registry.py:46–49,110–114` 要求 `muse={}` 和本机绝对 `legacy_state_dir`，没有 remote URL 或 Muse v1 factory。
- `hooks/wechat-inbox-watch.sh:5–7,19–31,70–120` 从平台本地路径读写状态，通过平台 runtime 的 `wake` 唤醒；wake 成功不是 worker 已执行或手机收到。
- 若中央收件放 VPS，须先由 01/02 定义一个正式远程 Muse executor：经过认证的领取/租约/完成协议、任务与尝试标识、期限、结果核验及 fencing。桥保留微信凭据和发送权；远程 executor 只返回该任务的结果，不获得任意 outbox 写权。不以 SSH 文件复制或共享 token 冒充已有适配。

### A.1 本轮实证：发送 unknown 尚未进入切换门禁（P2，01 必修）

独立 QA 用真实公共 dispatcher/outbox 组合与合成 HTTP 回包丢失复现：PEPE final 后 `jobs=succeeded`、`outputs=admitted`；发送模块把该回复归入 `outbox/failed`，`delivery_state=final_inflight_v1`、`delivery_outcome=unknown`。随后 `/backend codex` 仍把路由由 pepe 修订为 codex，并发出“已切换”回执。

- 证据：本批 `runtime-independent/UNKNOWN-DELIVERY-SWITCH-OBSERVATION.json`；固定源705232a，纯合成 wire、无真实 socket、产品源改动0。
- 原因边界：`dispatcher.py:95–102` 的 `_busy` 查公共 job、prepared/publishing/unknown 输出及 pending/sending 文件，但未查 failed 中的未知发送；`:135–136` 的状态提示只看 `outputs.phase=unknown`。`admitted` 是已入 outbox，不能证明送达已明确。
- 当前范围：独立 PEPE 配置只启用一个目标，没有本次复现中的可切后端；结果未知没有触发自动重发，也没有把仍在执行的 PEPE job 释放后重做。不能扩张称已经造成线上串线或重复执行。
- 责任与验收：01 在单入口切换批次中纳入所有待核发送状态、可见状态提示和受绑定的人工核对/解锁流程；补“final已完成+发送未知→拒绝切换”、`/status`可见、重复查询不重发、确认原发送事实后受控解锁、跨账号/epoch不能代解锁的组合验收。若正式 QA 将其列作本轮发布阻塞，由00按范围退01处理；本规划不替发布方解除门禁。

### B. 不能直接修改现有配置就切换

- `backend_state.py:19–22,48–50` 将 owner、bot、整个 config_digest 和 Store 路径绑定到受管数据库；`backends/registry.py:193–212` 复核相同绑定。给现有 PEPE `backends.json` 直接加一个 Muse 配置，会改变 digest，保护机制会拒绝继续。
- 单入口须有可审核的状态迁移：先确认没有进行中/未知任务和待发回复，保留旧完整配置、代码、依赖、收件回执、游标与远端 task 映射；使用隔离测试状态演练。正式迁移不复制未知身份、不清空账本、不回滚游标；没有可靠归属时暂停相关步骤。
- `serve.py:1381–1406` 的 bot 锁只保护同 OS 用户的本机 runtime；不能据此证明跨主机互斥。正式切换必须先确认旧 receiver 停止，再启新唯一 receiver；长期双机主备若需要，另设计有 fencing 的接管协议。

### C. 附件不是在统一模式下已经兼容

- `serve.py:1616–1625` 在任意 managed config 下设 `_attachments_disabled=True`；`attachment_runtime.py:162–164` 因而关闭附件箱。现有 Muse legacy 和 PEPE 的配置组合不能自动保留 Muse 的附件箱新功能。
- `pepe_core.py:92–117` 首期明确只收一对一纯文字，拒绝媒体/引用，`120–146` 每次只冻结一条 user 消息，session_id 为 None。
- 因此初版单入口应明确限文字，或由 01 先补“按目标能力决定收存/引用/发送”的公共接入，再保留 Muse 附件路径。不能静默退回旧媒体逻辑后宣称功能没少，也不能把发送给 PEPE 的图片只剩文字提示当图片理解成功。

### D. 账号、回复授权与模型记忆分开

- `serve.py:250–267` 只接已登录 owner 的一对一消息；`66–84,128–149,167–177` 将 context_token 和原消息归属持久保存。`dispatcher.py:104–113` 原样关联到该任务回复；`serve.py:1271–1283` 仅在同用户、同登录 epoch 条件下采用最新 token，并拒绝跨 owner 收件人。
- 当前 `context_token` 用于微信发回授权，不是模型记忆。新中央协议应把它留在 receiver 一侧，结果通过受绑定 job ID 回来后由统一 outbox 发送。不同 bot/账号的 token 不共享。
- `dispatcher.py:209–215,265–267` 对 backend/instance 分隔 conversation，PEPE 不复用 session ID。PEPE 原生任务设置“沿用同一聊天”只证明任务侧的配置，不能证明与电脑主聊共用历史。

### E. 断线、取消与恢复按事实收口

- 微信收件 `serve.py:1776–1807` 是全批持久化后才推进 cursor，持久回执去重；这保护桥自己的重复投递，不保证平台保留所有断线前未读消息。
- PEPE 路线须在恢复连接/订阅后主动对**该专用队列**补查 queued 并按已有 task ID 核对 in-flight；不依赖事件回放，不凭“订阅启用”判自动接单。当前 handler 已每次事件先 list_tasks，但冷启动、订阅过期及长时间无事件的恢复仍需独立验收，未在本方案中实测。
- `backend_state.py:87–96` 重启将活跃任务和 publishing 输出转为 unknown；`dispatcher.py:255–260` 在 unknown 前停止新任务自动推进。不能把“程序重启了”当业务已经恢复。
- `backends/pepe.py:485–486,510–525` 把远端终态、取消和关闭保守标 unknown，原因是没有可信的远端停止证明；不能为顺滑切换把它改成 cancelled 后再送 Muse。
- 首期切换继续串行，避免两助理同时改变同一任务；后续并行两份结果或显式转交要另有独立任务、输入摘要和来源标识。

## 分阶段可观察验收

| 批次 | 必测情景 | 必须看到的证据 |
|---|---|---|
| 双桥并用 | 两个现有隔离入口各发无私密文字，再交错发送；同一时段一边断开/恢复只影响自己 | 各自 bot/owner 指纹与实际加载源、唯一 receiver、任务/结果归属，微信接口接纳与手机实收分列；不从相同名称推断身份 |
| 单入口文字切换 | 查看当前助理；空闲 Muse→PEPE→Muse；排队、运行、待发、审批、unknown 时尝试切换；旧回复迟到 | 已收消息始终属于原目标；拒绝忙切换；只用该账号/peer授权发回；无重复任务/跨后端兜底；手机明确知道谁在回答 |
| 故障与恢复 | receiver 重启；PEPE final 后发送 API 响应丢失，再尝试切换及查询状态；PEPE 通知漏达或订阅恢复；模型侧取消未获停止证明 | 游标不倒退；同任务最多一次新提交；未知发送时拒绝切换、状态可见、核对后才解锁；unknown 不重投；旧任务映射保留；补扫取得明确结果后才完成核对；证据不足则维持待核 |
| 附件与交接 | 同样的图片/文件在 Muse 路线保留原能力；PEPE 拒绝不支持输入且不冒充看图；显式文字摘要转交 | 原字节/索引/任务引用隔离；不能将附件内容当权限指令；两端记忆不自动合并；真实媒体另验 |
| 回退 | 从候选统一入口退回原配置和唯一 receiver | 真实进程身份核对与停止证据；旧运行包/依赖/Hook可恢复；保留全部任务、回执、游标与unknown；不把回退等同远端任务停止 |

## 尚需用户决定

推荐先批准“两个桥独立并用的联合验收”，然后再决定统一收件的宿主和是否进入单入口文字切换实施。待核的关键事实是：现有微信账号与两入口使用体验、Muse 云机的受限出网/生命周期、single-store 队列接管与状态迁移方式、保留附件能力的公共改造。现在不要求用户先选具体协议、数值或新增凭据。
