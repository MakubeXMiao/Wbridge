# wbridge 协作分工与接入线扩展规则

日期：2026-10-23（Asia/Shanghai）。状态：当前五对话组织结构与后续编号规则按用户决定更新；协作细则供用户审阅。本轮只记录与整理，不派发开发任务，不修改业务代码。

## 1. 已明确的项目规则

1.1 本项目当前采用以下五个对话：`00 总控框架`、`01 公共底座`、`02 Muse 桥`、`03 Codex 桥`、`04 CC 桥`。公共底座独立为开发线，不再由 Muse 线兼管；后续按第 1.7 节扩展。

1.2 用户已明确：当前 00 以后只承担发布与收集汇报；公共底座与三条接入线的开发在各自对话内完成。00 不实现公共底座，也不代开发线修业务代码。历史交接中由总控承担公共代码实现的安排，以及上一版草案由 Muse 线暂管底座的建议，均由本次分工替代。

1.3 用户可在任一对话提出修复、修改或新功能。接收对话负责先记录，再按归属处理；不能要求用户为了登记而到多个对话重复描述。

1.4 聊天编号与职能角色编号分别使用。例如，聊天 02 是 Muse 开发线，不等于中枢角色 02 架构官；聊天 01 公共底座也不等于角色 01 产品官。

1.5 用户已确认现有对话改名及四条开发线建立；00 已现场看到四个开发工作树。对话标题与工作树的一一对应仍须各线自报核对，不能从随机目录名猜测。对话建立、任务投递与规则已接收分别记录。

1.6 五对话组织结构和公共底座独立归属是用户已决定事项；具体文件归属、共享记录目录和执行细则仍为待审建议，不作为已派发的开发任务或已生效的全局角色规则。

1.7 后续新增 Agent 接入线继续使用 05、06、07……，保留既有编号，不因新增接入重排原对话。00 固定负责发布与汇报，01 固定负责公共底座，02 起是可扩展的 Agent 接入线；这些编号不对应中枢职能角色。

1.8 用户说明当前项目基于 wx；结合已交接项目，本文将 wx 按微信理解：微信 ClawBot / iLink 是当前消息入口，公共桥接能力服务于各 Agent，产品不绑定 Muse 或某一执行后端。更多 Agent 的编号规则已确定，但其实际接入能力仍需逐项实现和验收。

## 2. 已确定的职责与建议边界

| 项目对话 | 常设责任 | 开发与发布边界 |
| --- | --- | --- |
| 00 总控框架 | 接收需求入口、汇总各线记录、整理负责人/依赖/版本范围、收集独立 QA、准备集成候选和发布记录 | 不编写业务实现；代码冲突或集成缺陷退回责任线；推送、部署、发布按具体授权执行 |
| 01 公共底座 | 公共微信收发、媒体、队列、状态、路由、CLI/打包与公共契约；牵头跨线架构 | 独立开发、自测与交接；三条接入线通过已确认接口使用公共能力 |
| 02 Muse 桥 | Muse 适配、唤醒/回调/会话/恢复 | 开发、自测、交接在本线；既有 Muse 修复继续保留真实环境待验状态 |
| 03 Codex 桥 | Codex 执行、续聊、事件、取消及结果回传 | 只实现本线与已确认的公共接口；需要改公用代码时先提出变更请求 |
| 04 CC 桥 | Claude Code 执行、续聊、审批、取消及结果回传 | 只实现本线与已确认的公共接口；需要改公用代码时先提出变更请求 |
| 05、06……后续接入线 | 各自新增 Agent 的执行、会话、状态及结果回传 | 沿用 01 的公共契约与本线工作树；新增时登记名称、编号、负责人及能力验收范围 |

2.1 **公共底座由 01 独立负责。** 现有实现仍有公共能力与 Muse 接入耦合，01 先梳理边界和契约，02 提供现有 Muse 行为与兼容性要求，03/04 提供各自接入要求。职责拆分不代表现有代码已经完成拆分。

2.2 建议公共范围包括现有 `wechat_bridge/ilink.py`、`crypto.py`、`media.py`、`store.py`、`serve.py`、`worker_state.py`，以及公共 CLI、打包入口和离线测试入口。`cli.py`、`pyproject.toml` 等也不能被三条接入线各自改成独立发行实现。最终文件归属和适配器目录由后续架构任务确定，本草案不预先规定新目录/API。

2.3 公共契约由聊天 01 牵头、按需采用中枢角色 02，产出消息、附件、会话、状态、结果、取消与审批的方案。聊天 02/03/04 及后续接入线提供接入要求；跨线方案经用户确认后实现。00 收集决定和协调依赖，不承担方案实现。

2.4 建议同一公用文件同一阶段只设一个实现负责人。跨线任务可以拆子任务，但保留一个总负责人；三条接入线不各复制一套微信收发服务，也不同时轮询同一个 bot。

## 4. 需求从任一对话进入

4.1 接收即记录，建议编号为 `WBR-<入口对话编号>-<日期>-<序号>`，当前入口为 00～04，后续可新增 05、06……，例如 `WBR-02-20261023-001`。不同入口保留各自编号；00 合并重复需求时保留原编号和关联关系。此前已登记条目如使用旧聊天编号，应保留原编号并注明当时名称，不因改名重编号。

4.2 最小字段：用户要求摘要、来源对话与时间、任务类型、所属模块、负责人、验收标准、状态、依赖、相关提交、测试/QA证据及发布归属。涉及金额、账号、数据迁移或外部操作时，另记录具体授权范围，不保存凭据或完整私聊内容。

4.3 已明确授权且只影响本线的改动，在该线记录后继续执行，不必逐项等待 00 重复确认。若需要改公共契约、他线文件或发布范围，接收线先登记依赖和待决定项，统一交 00 评估，再由 00 派发 01 等责任线；不绕过 00 直接向其他线派单，不静默越界。

4.4 在 00 提出的开发需求，由 00 登记并整理建议归属，开发在对应对话执行；不会因为需求从 00 进入，就在 00 编码。在开发线提出的他线需求，也先记下，再交相应负责人。

4.5 状态至少区分：已登记、待决定/依赖、开发中、已自测、待独立 QA、待真实验收、待发布、已发布、阻塞、取消。任务不需要真实环境验收时注明不适用及依据；不能把“开发完成”直接写成“已发布”。

## 5. 跨工作树记录方式建议

普通 Git 文件在不同 worktree 中不会自动更新，不能把同名台账当成实时共享状态。

5.1 建议采用一个**本地共享协调目录**：在每个工作树运行 `git rev-parse --path-format=absolute --git-common-dir`，得到共同 Git 目录，在其中使用 `wbridge-coordination/`。本机对应为主仓库 `.git/wbridge-coordination/`，主工作区与各开发工作树读取同一个物理位置；新增 01 工作树后也按此接入。

5.2 建议各入口只写自己的目录：`intake/00/`、`intake/01/`、`intake/02/`、`intake/03/`、`intake/04/`；四条开发线只写自己的进展报告 `reports/01.md`、`reports/02.md`、`reports/03.md`、`reports/04.md`。任务记录按编号独立成文件，保留来源和修改时间。原始来源/要求由接收入口维护；跨线承办者沿用原任务编号在本线报告更新状态，不改写他线的原始收件记录。

新增接入线时按编号增加自己的 intake 目录与报告文件，例如 `intake/05/`、`reports/05.md`，沿用同一套收件、汇总与独立 QA 规则，不另建一套总台账。

5.3 只有 00 写总台账、跨线依赖、版本候选和发布记录。00 在用户要求收集汇报、准备发布或处理新需求时读取各入口与报告，汇总时注明更新时间；各线不直接并写总台账。

5.4 该目录是本机协作状态，不通过 Git 自动同步，不等于后台服务、消息通知或云备份。已确认分工、重要决策与脱敏发布快照可以另存仓库文档；迁移机器前需单独保留需要的协作记录。

5.5 用户已要求安排首轮工作并索取 Muse 实测，00 因此准备上述共享协调目录与任务记录，不建立后台轮询或定时任务。Muse 客户端“微信桥”报告的索取与版本核验由 02 执行，00 只收 02 汇报。仍须让四条线分别接收并确认同一规则版本；不能把主工作树新增文档视为其他对话已加载。实际投递、接收与执行以台账证据为准。

## 6. 每次汇报的固定内容

各线结束一次工作时更新本线报告，至少包含：任务编号、当前分支与提交、完成内容、改动文件、自测结果、独立 QA/真实验收状态、未解决问题、跨线影响及下一步。需求变化由收到该次变化的入口在自己的 intake 新增变更条目并关联原任务编号；承办线更新本线报告，00 将已确认变更汇总到总台账，避免多人改写原始记录或只记在聊天正文里。

00 汇总时保留各线报告时间和证据，区分“对方自报”“已读取提交/测试记录”“独立复核”“用户实测”。没有报告或证据时写未知/待补，不据沉默推断完成。

## 7. 集成与发布

7.1 各线交付任务分支和具体 SHA。00 可以准备集成候选；机械合并遇冲突或发现业务问题时，退回负责人修复后重新提交，00 不改业务代码解决。

7.2 独立 QA 检查最终候选提交，FAIL 按需求、契约、体验、实现或发布配置退回责任方。候选代码变化后，原 QA 结论不能自动覆盖新提交。

7.3 真实微信/Muse 云环境/手机送达按任务范围单独验收；既有导入基线的离线 PASS 不替代这些验收。发布前明确版本、目标、QA证据、真实验收结果、授权范围与回滚方案；工作模式确认不等于授权今后所有推送或生产部署。

7.4 发布后由 00 记录实际目标、版本/SHA、结果、回滚位置与未完成项。各线不绕过 00 各自发布正式版本。
