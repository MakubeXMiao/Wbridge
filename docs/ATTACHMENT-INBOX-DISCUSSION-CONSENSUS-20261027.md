日期：2026-10-27，北京时间。任务：WBR-00-20261027-002。

**结论：三轮讨论后，00 与 Muse 对基本方向达成共识。现在完成的是讨论和方案修订，没有改业务代码，没有部署，也没有产品 QA 或手机实测通过的结论。**

完整候选见 [R2 修改计划](ATTACHMENT-INBOX-PLAN-20261027-R2.md)。它共 12 节；Muse 已核对全文、末句、29,583 字节、12,177 字符及完整哈希一致。第一稿原件保留，不覆盖历史版本。

## 1. 共同认可的做法

1.1 **先解决两个不同的使用问题。** 附件箱负责“中午收下的文件，晚上找回来”；即时图片引用负责“刚发图，下一条文字马上问这张图”。只做搜索目录，不能冒称即时对话已经连贯；延长等待、修改提示词也不能单独解决跨批引用。

1.2 **附件原样保存，保存和看懂分开。** 图片、文件、视频、可下载语音按收到的解密字节保存，不二次压缩、不执行、不解压。打不开的文件仍可成为普通附件。HEIC 的原件收存/文件取回，与模型识图/手机预览分开验；语音原件按文件发回，与原生语音气泡分开。

1.3 **不能用“解密没报错”冒充正确。** Muse 收回了原稿中“padding 通过就当成功”和“不同候选按评分选一个”的建议。00 也纠正了另一种过度保守做法：不能把正常可读图片、未知格式和真正解密冲突统统标为待确认。正常有效图正常收存；仅不支持预览就如实说明；冲突未决才标解密待确认，不猜根因、不拿错字节发回。

1.4 **即时图片引用由公共层维护唯一来源。** 保留最近图片组的来源、时间、原序号、附件编号和状态。失败的第一张仍占第一张，不能过滤后把第三张变成第二张。文字到达时固定它指向的图片范围；后来新图不能把原句的对象换掉。每次取用按这份固定快照校验，模型必须实际读到指定图片，不能只拿编号或摘要回答。

1.5 **遇到不明确的指代，先辨清对象。** “这个多少钱”也可能在问文字或新话题，不能只因最近有一张图就强行关联。使用关联时自然说明用了哪张图，便于用户纠正；多张、未收完、已失效或有冲突时简短澄清，不偷偷退回旧图。图片下载前就应登记待处理位置，避免正在下载的新图被忽略。

1.6 **多件发回按实际发送数量管理。** 一条配文、几张图片、长文本分块会占多个发送单位，不能都算成“一次回复”。发送前先算本页预算；不足就分批。已发、明确未发、结果未知分别保存；重启不能抹掉计数或把未知结果当成未发。用户换话题时，不自动继续发送旧附件。

1.7 **长任务保留真实进度，不拿正式回复当占位。** 当前正式 reply 会完成本批，先发“稍等”会失去同一句柄的最终提交机会。本批先做有实际进展的续租与阶段回调；进度通知另需契约，不能假设换个句柄就获得旧任务权限。收件、保存、Muse 接手、接口接受、手机收到分别验。

1.8 **不让清理功能拖垮核心，但也不无限占盘。** 实际自动删除后置；第一版仍需容量计量、清理预览、在用/重要保护和满额拒新。满额只影响新增附件，文字/查询仍响应；已有文件不悄悄删除。生产清理、私人失败取样、历史数据导入均未执行。

## 2. 互审确实纠正了什么

| 对方指出的问题 | 复核与修订结果 |
| --- | --- |
| Muse：第一稿漏了图后文字即时追问 | 00 接受，R2 新增完整第 9 节，加入固定快照、失败序号、真实读图及测试 |
| Muse：单文件回复和“8 条”缺证据 | 双方复读固定 012，确认单件限制；8 条只是本进程本地计数，非微信统一规则，非持久预算 |
| Muse：多件会消耗文字、配文和媒体多个单位 | R2 明确物理计数、预算预留、未知占用、跨重启与分页，工作量按“大”评估 |
| Muse：大版本一次做完容易卡住 | 00 接受 A/B1/B2/C 分阶段，每阶段给退出标准；单件里程碑不能冒称完整首版 |
| 00：只改提示词不能管住自动续发 | 直接核到旧发送层自动更新回复上下文的路径，R2 要求新回传组在公共发送层限制它 |
| 00：每次重读“最新图片组”可能换错对象 | 重读固定截止位置的参考快照；默认最近组与已经绑定的快照寿命分开 |
| 00：“文件与数据库同一事务”说法不现实 | 文件安全发布，索引与引用在数据库内共同发布；另做阶段记录、中断恢复和对账 |
| 双方：旧失败率、已有诊断和续租不能混写 | 旧 2 成 8 败不归给 012；已补诊断不重复造；提示词写了续租不等于实际执行过 |

## 3. 怎么拆才有实际交付

| 阶段 | 交付与验收例子 | 难度判断 |
| --- | --- | --- |
| A：内部基础 | 一件附件存下、跨批找回、原字节一致，写一半退出可恢复，同名不误取，满额可解释 | 中，收发能复用，目录与恢复是增量 |
| B1：先改善日常体验 | 图后文字能接上；九张中点名第 2 张不串图；失败、晚到新图、重启和失效诚实处理，模型真看过图 | 中，难在顺序、归属与状态一致，不是只加提示词 |
| B2：完成多件闭环 | 多件按序回传，部分失败不说全完成；预算耗尽有进度，明确继续才续发，重启/旧版本不误完成 | 大，涉及队列表示、预算、未知结果及回滚兼容 |
| C：实际清理后置 | 清理预览和版本边界先验；生产删除另有清单与窗口 | 大，涉及索引引用、在用保护、竞态和原未知阻塞 |

A、B1 可以分别成为内部或局部候选，不能把局部体验称作完整首版。约定完整首版仍需 A+B1+B2 与连接稳定链验证。没有承诺今晚或几小时内全部实现。

## 4. 仍待决定与落实的部分

4.1 **用户取舍尚未拍板：** 普通附件 30 天、总量 5GiB、重要可钉住；最近图片组可查到下一组或最长 24 小时；模糊短句自动关联如 15 分钟；最多 16 个原位置。上述都只是候选。短窗口不是拒绝较晚的明确指代，引用过期也不是删除原件。单件 100MiB 沿用现有本地边界，不声称是平台官方上限。

4.2 **01 还需把候选写成具体公共契约：** 附件索引与参考快照字段/版本、非敏感登录代次、恢复阶段、物理预算持久记录、回传组类型与明确续发授权、旧任务兼容和回滚门槛。正常新增图片不应改变已有合法快照。

4.3 **02 还需验证真实接入：** 受控查目录与取图流程、实际可用读图工具、路径和格式可读能力、平台真实采用提示词、长步骤能否及时续租。讨论不能替代这些验收，不假设 Muse 已通过新接口读到图片。

4.4 **未证实或继续搁置：** 真实 AES 根因、当前 GC 原始阻塞首因、云端连续多日稳定性、真实手机效果；近期文字归档、每日汇总、待办文件、48 小时摘要、未定任务标签和语音问题不进入这一批实现。原版、账号、投递到微信需求收件箱、03/04 和其他任务不动。

## 5. 对 R2 的两条解释性修正

5.1 R2 第 2.1 节的 Mac 工作树路径只说明本轮静态阅读的位置。**源代码基线按固定 Git 提交 e804be792ef08e985f94d7536c2926a597391150 唯一识别**，不拿本机路径证明云端加载版本。云端解释器、包与 dirty、Hook/prompt、实际加载与重启要在未来更新前另行绑定；本轮没有重新核这些运行事实，不能把未核云端包称为另一份权威源码。

5.2 正确顺序是：用户确认方案取舍 → 01 牵头公共契约、02 复核接入 → 按规则确认契约 → 责任线实现与自测 → 最终固定版本的非实现者 QA → 用户审候选 → 另获部署授权后才部署。独立产品 QA 需要已有实现，不能写成“QA 之后才谈写代码”；也不能把允许写代码当作允许部署。

这两条以本附记和已发 Muse 的收口回复说明；R2 经双方核过的原字节不追改，便于审计与复现。
