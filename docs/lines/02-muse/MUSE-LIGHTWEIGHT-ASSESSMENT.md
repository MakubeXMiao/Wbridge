## 1. 判断

**保留 Python 常驻收发、持久队列和防重；优先简化模型承担的桥接操作。** 这是当前代码与单人低吞吐需求相符的候选方向，不需要先换语言、数据库或重写框架。当前 Muse 接入仍依赖 Hook 唤醒和模型正确执行机器协议，尚未证明可达到稳定、低延迟的日常助手体验。

用户看起来很小的任务，也可能包含慢网页、图片下载或外部工具；不能假定小任务一定能在 90 秒内出现有效进展。稳定性还包含“已接收有据可查、出错可见、重启能续、业务动作不重复”，不能只看最终有没有生成一句回复。

## 2. 当前代码实际如何工作

```mermaid
flowchart LR
    W[微信 iLink] --> R[常驻 Python 收件]
    R --> I[持久 inbox 与收据]
    I --> H[Hook 巡检与 plan]
    H --> P[Muse 平台启动 worker]
    P --> B[模型调用 begin]
    B --> M[理解任务与工具执行]
    M --> Q[模型 refresh 或 reply]
    Q --> O[持久 outbox]
    O --> S[独立发送线程]
    S --> W
```

现有简单快路径已经是 `begin→reply`。Hook 定义明确不强制等待 5/8 秒、不写临时正文、不额外查无关历史，复杂任务才按实际进展 refresh。它减少了协议调用，但模型仍须正确执行。

源码：`hooks/wechat-inbox-watch.json:6`；`hooks/wechat-inbox-watch.sh:17–45`；`wechat_bridge/worker_state.py:327–403`。

## 3. 应保留的可靠性机制

| 机制 | 对私人助手的意义 | 代码依据 |
| --- | --- | --- |
| 常驻收发与持久队列 | 进程重启可保留收件和待发回复 | `serve.py:79–139`、`store.py:120` |
| 单实例、单发送者 owner | 减少抢收、混批与重复处理 | `serve.py:747`、`worker_state.py:327–376` |
| 收件安全落盘后推进游标 | 失败时保留重投机会 | `serve.py:1206` |
| 固定回复身份、入队前 fencing | 迟到 worker 不能用旧身份提交回复 | `worker_state.py:440–512` |
| 分片进度、有限重试、未知结果保留 | 避免重启后从头发送或把未知结果当未执行 | `serve.py:635–711`、`worker_state.py:514` |

这些是低流量也需要的安全性，不应为了省调用而删除。源码有保障不等于已独立通过手机送达验收；微信服务端对 client ID 的去重语义仍待实机确认。

## 4. 与稳定、快速小任务不匹配的部分

4.1 **模型同时负责业务与运行协议。** 一个 prompt 要处理 wake reason、路径、事件/私有 lease、后到消息、续租、完整 ID、失权退出和结果不明。代码能拒绝非法提交，却不能强制模型准时调用或按用户意图回答。`refresh()` 目前验证身份和时间，并不独立验证业务“真实进展”（`worker_state.py:387–403`）。

4.2 **平台启动仍是外部依赖。** 代码的事件未开工窗口为 180 秒，开工后软租约为 90 秒、硬上限为 begin 起 570 秒；这些是本地状态期限，不是平台启动或手机响应承诺（`worker_state.py:22–29,106–120`）。当前没有证据说明换短 prompt 或增加轮询就能消除分钟级等待。

4.3 **收件路径会等待附件。** `handle_incoming` 同步下载附件后才写 inbox（`serve.py:221–263`）；每下载源 timeout 为 120 秒（`media.py:66–83`）。媒体慢时同批后续文本及下一次拉取可能一起等待。`received_at` 在这段下载后写入，也可能使现有阶段统计漏掉媒体前置耗时（`serve.py:117`）。这是代码结构风险，尚非今早图片故障的已证实根因。

4.4 **发送保序有速度代价。** 只有一个 flusher，媒体上传可阻塞，且前条退避会阻止同一收件人的后续回复（`serve.py:869–872,933–962`；`media.py:186–250`）。保持 FIFO 有防乱序价值；若改变快答与媒体的优先级，需先明确契约，不能擅自插队。

4.5 **缺少私人助手的业务状态。** 所查 CLI 只有登录、收发和状态命令，Store 是桥接数据；仓库没有待办实体、到点调度、修改/取消和重启后补执行的业务契约（`cli.py:378`、`store.py:35`）。5 秒 Hook 巡检不是提醒调度器。Muse 平台是否另提供这类能力须单独确认。

4.6 **回复防重不自动保护业务动作。** 当前 `client_key` 和 reply_batches 记录的是微信回复（`worker_state.py:250,483–507`）。如果 worker 已创建一个提醒，随后在入队回复前失权，仓库没有记录该提醒外部 ID 的业务动作账本；接管者能否避免再创建，取决于尚未验证的 Muse/工具能力。`release` 也不代表已终止外部工具（`worker_state.py:405`）。

4.7 **长期历史扫描可后续测量。** covered 会扫描队列及 reply_batches，部分操作在锁内且批次没有自动 TTL。当前无证据表明这是今早主要瓶颈；不因看到扫描代码就迁移数据库或删除防重记录。

## 5. 容易走错的简化方向

- 正常 helper 回复带 `client_key`，会跳过 20 秒机械合并；不能把该常量直接算入首回预算（`worker_state.py:483–486`、`serve.py:505–510`）。
- 不能把 begin 提前到 Hook wake 之前来省一步，否则平台排队会消耗 90 秒运行租约。应在真实 worker 开始后才取得执行身份。
- 不能用脱离任务的后台心跳长期续租；需要可核实的任务/工具进度、硬上限、取消与 fencing。
- `wechat-bridge send` 直接走网络、每次生成新身份，不能用它绕过正式回复队列图快（`cli.py:254`）。
- 增加“收到”消息会消耗上下文发送预算；只能表示真实持久接收，不能冒充业务已完成，也不宜每条刷屏。
- 今早约 509 秒含人工入队；约 197 秒至自报 begin 的区间缺平台启动证据。二者都不能直接用于决定放宽哪一个计时器。

## 6. 候选方案与取舍

| 候选 | 适用条件与收益 | 限制/代价 | 当前建议 |
| --- | --- | --- | --- |
| A：保留 Hook，收窄 worker 指令与桥接操作 | 继续利用个人 Muse 现有工具；改动边界较小 | 平台排队/启动仍在关键路径，单靠缩短 prompt 无延迟保证 | 作为近期兼容候选 |
| B：受控适配器管理机器协议，Muse 主要理解/执行任务 | 安全传参、lease、批次、结果与进度由代码管理，减少模型操作走样 | 依赖正式可用的 worker/工具生命周期、结构化结果、取消能力；当前仓库未证明个人 Muse 支持 | 目标方向，先核平台能力再定契约 |
| C：确定性的待办/提醒状态，小查询按能力交 Muse | 业务状态可查、重启恢复、到点触发不依赖模型长时间等待；清晰的已接收/处理中/完成/失败状态 | 新增业务能力和动作幂等，需要公共 01/本线 02 分工；自然语言理解仍可调用模型 | 与 A/B 组合的产品候选 |

推荐保留当前底座，以 A 限定现有链路，同时评估 C 的业务状态需求；B 在平台能力证实后再组织设计。以上是探索判断，不是最终架构或实施排期。

有副作用任务应使用跨 worker 接管不变的动作身份，保留“未执行/已成功/结果未知”和外部对象 ID；不能将“未知”直接重做。取消、失权及外部工具结束也应分别核对。具体契约归 01 牵头、02 提供 Muse 约束，用户经 00 组织确认后实施。
